# S11 封存關聯化設計草稿

主辦確認 S11 賽季結束及最後發布版本後，將封存後仍需查詢的賽季資料整理成關聯表。封存沿用 `s11` 和既有公開入口。原始 JSONB、營運資料與修訂紀錄留作查證及回復來源。此設計以 `8da8f2f6` 為基準，於封存時重新核對實際資料及程式版本。 [#980](https://github.com/OCLR-dev/OCLR-website/issues/980)

## 現有流程與 S11 的差異

現行 `archive` 指令接受已結束、未發布、無報名設定及營運資料的賽季。S11 的封存需處理營運資料，因此需要專用的轉換及切換流程。歷史統計支援清單目前包含 S1–S10，S11 的頁面、API 與背景分析也要在封存時一併接入。 [封存指令](../src/lib/tournaments.ts) · [歷史統計支援](../src/lib/archive-statistics-model.ts)

既有歷史讀取層已有具型別的檔案、MP 審核資料、公開統計摘要與成績列。S11 優先沿用這套編碼、版本核對及驗證流程。仍需查詢的賽季設定欄位，以及現行歷史模型無法完整表示的 S11 規則或決策，在資料盤點後補上具型別的欄位或子表。 [歷史關聯讀取](archive-relational-queries.md) · [JSONB 盤點](archive-jsonb-inventory.md)

## 資料映射與發布範圍

| 資料                     | 封存來源                                                                                             | 轉換與驗證                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 賽季設定與規則           | 封存時確認的 `edition_state` 與對應 `edition_revisions`                                              | 關聯化封存頁面仍需讀取的標題、規則、階段與時區等欄位。保留設定版本、文字與順序。                                       |
| 玩家、隊伍與選秀         | 已接受報名的公開身分、隊長及隊伍的個別發布狀態、已發布選秀快照                                       | 沿用 osu! ID 與隊伍識別。按各自的發布條件映射名單、選秀順位及隊伍資訊。                                                |
| 賽程、對陣與圖池         | 已發布的比賽及圖池版本，連同賽果審核引用的圖池快照                                                   | 保留比賽 ID、原賽程、對陣來源、圖池格位、譜面 ID 和順序。分別保存圖池公開版本及每場審核引用版本。                      |
| 賽果及逐圖成績           | `match_results.published_revision` 指向的已核准 `result_revisions`，及該修訂指向的 MP 匯入與比賽資料 | 比對比賽 ID、修訂、MP 指紋及 game ID。官方比分與逐圖資料分開映射，保留審核納入／排除、替補歸屬、規則、實際分數和缺值。 |
| 報名答案、資格與可用時間 | 現有受權限保護的紀錄及歷程                                                                           | 保存在原有私有範圍。封存後仍需私有查詢的欄位依用途轉成受限關聯資料，公開封存投影只取已發布欄位。                       |
| 來源與稽核               | 原始 JSONB、營運表、核准與發布修訂、來源 MP 及操作事件                                               | 保存原內容與識別對應，用於追溯、驗證與重建。                                                                           |

公開賽果以每場的發布指標和核准狀態為準，並使用該修訂引用的隊伍、名單、圖池與規則。比對保留原始分數、依政策計算的有效分數，以及官方比分三者的含義。S11 使用的特殊賽制、重賽、裁定與替補歸屬須以實際發布資料演練。 [公開賽果查詢](../src/lib/public-competition.ts) · [已發布對局明細](match-details.md)

## 建立候選版本與切換

1. **固定來源。** 主辦確認最後發布版本與封存截止點。從一致的資料庫快照記錄賽季設定版本、各場發布修訂與來源指紋，以及已發布圖池和名單的版本。保存封存前公開查詢的比對資料。
2. **建立候選。** 依版本清單映射封存資料，為原始賽季、比賽、隊伍、MP 與譜面建立可追溯的識別對應。以 `s11` 加來源版本與內容摘要辨識同一候選。重跑相同來源時沿用候選與統計世代。來源變動時建立新候選供審閱。
3. **驗證候選。** 在隔離 PostgreSQL 演練轉換、關聯還原、統計回填及重跑。候選的設定版本、來源指紋與關聯頭必須一致。遇到映射缺口或發布範圍差異時列出受影響的比賽或資料類型，補齊後再驗證。
4. **切換公開讀取。** 正式切換前依部署流程取得可還原備份。實作專用操作，鎖定賽季及其發布寫入，在同一交易重查來源版本並啟用完整候選。已驗證的關聯頭、統計世代與公開設定須一起生效，既有 `s11` 網址以保留的識別讀取對應資料。
5. **回復及重建。** 留存切換前的公開設定和版本指標。切換演練須驗證可回到該發布版本，並能從保存的來源重建封存候選。現行 `OCLR_ARCHIVE_READ_MODEL=jsonb` 是封存讀取層的回退選項，S11 回到封存前營運讀取需要另外驗證切換狀態。 [部署與備份](deployment.md) · [關聯資料回退](archive-relational-queries.md)

交易鎖與版本檢查須涵蓋可能變動公開資料的路徑，包括賽果發布與撤回、圖池發布、名單變更。先在隔離資料庫驗證並行寫入與中斷後的重跑，再確定正式操作順序。正式封存由主辦核准後執行。

## 驗收條件

- **公開資料一致。** 以封存前最後發布版本核對比分、比賽與逐圖成績、隊伍名單、選秀、賽程及圖池。涵蓋已撤回、尚未發布及部分缺值的資料。原有比賽與選手入口維持可查。
- **分析一致。** 以相同發布輸入核對 S11 個人、賽事及逐圖分析，並保留官方比分與現有評分政策。跨季統計以加入 S11 後的完整發布輸入核對，驗證 S1–S10 的來源與賽季結果仍可重現。 [背景玩家分析](background-player-analytics.md)
- **關聯資料就緒。** 核對 S11 文件及原生欄位與來源一致。既有 `db:normalize-archives` 驗證須顯示 `archiveReadReady: true`、`stale: 0`、`obsolete: 0`。公開統計驗證須顯示 `publicReadReady: true`，重查的筆數與世代識別一致。實作需先將 S11 納入這些流程的涵蓋範圍。
- **權限與版本完整。** 驗證匿名公開、本人及授權工作人員的讀取邊界，查核報名答案、資格、可用時間與未發布修訂。既有 API 以相同授權條件及回應契約核對。
- **失敗時可回復。** 演練來源在切換前更新、候選不完整、操作中斷及切換後回復。核對原始 JSONB、修訂與發布指標仍可查證。

封存時需確認實際的發布版本、需要保留的私有查詢，以及 S11 賽制與歷史模型的欄位對應。以主辦核准的對照結果作為切換依據。
